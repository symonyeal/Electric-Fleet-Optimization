# Electric Fleet Optimization

Reproducible models for electric-fleet routing, vehicle blocking, and charging planning.
Each reported outcome carries a feasible upper bound, a valid lower bound, and an
independent check, separating an operating insight from an untested assumption.

**Status: result-integrity repair, 1 October 2026.** A published result is admitted only
after its replay, lower-bound source, formulation, inputs, scenario, code identity, and
artifacts pass the result contract ([Validation](docs/VALIDATION.md)). Legacy bundles carry a
migration decision; dirty, stale, contradictory, and untraceable bundles do not support a
verdict. GitHub Actions runs the fast suite on every push and a separate pinned-EVRP-data job;
the rotating GTFS snapshot and slow experiments remain local checks. Benchmark runs longer than
a working session are recorded as they finish.

## Background

### The problem

Fleet electrification links vehicle availability, charging access, and grid demand. This
repository turns that planning problem into an auditable operating model, while keeping the
modelled case distinct from an agency operating plan or infrastructure authorization.

An electric fleet trades range for charging. A delivery EV that cannot reach its
next customer detours to a station; a bus that cannot finish its block needs a
charger, a plug, and grid capacity at the right time. These are integer decisions
coupled to continuous energy, and the coupling is where the cost of electrification
sits.

### What this computes

Two applications share one certificate core.

**Routing.** The IEEE WCCI-2020 competition published an EVRP benchmark whose report
lists values that "could be optimal in some cases but [are] not verified yet". Later
heuristics, among them [evrp-python](https://github.com/NeiH4207/evrp-python), report
shorter routes on six of its seven small instances. No method there reports a lower
bound. This project solves the benchmark's MILP where it can, bounds it by column
generation where it cannot, and states per instance whether a published value is
certified, refuted, or open.

**Transit.** TransLink publishes its timetable as GTFS. Given those trips and declared
battery, charger, and grid parameters, the models determine which buses and chargers
can operate the timetable and at what cost, from a battery-free fleet bound up to a
convex MINLP with charging losses.

The question common to both: what do the battery and charging constraints cost,
relative to the same fleet without them, and can the answer be certified?

### Where interior-point methods enter

They solve continuous problems; integer decisions still need branch-and-bound,
decomposition, or outer approximation. Here they supply LP bounds at inexact
branch-and-bound nodes, well-centered duals for column generation, and barrier
solutions of the convex charging subproblems inside outer approximation. The
mathematics follows Vanderbei, *Linear Programming* (4th ed., 2014), and Beck,
*Introduction to Nonlinear Optimization* (2014).

### Where it stops

Small instances. One depot, homogeneous vehicles, no time windows, no driver duties,
no distribution-network power flow. Benchmark distances are unitless. The Route 100
scenarios price energy with BC Hydro's published fleet tariff and take the pack,
consumption, charging efficiency and charger count from published sources; charger power,
the depot and the capital costs remain declared, not agency data ([Data](docs/DATA.md) §3). It does not reproduce TransLink
dispatch, authorize infrastructure, or match the speed of VROOM, PyVRP, or HiGHS.

## Run

Python 3.14 with numpy, scipy (HiGHS 1.12) and matplotlib; `data/evrp.py` fetches the
benchmark from evrp-python at a pinned commit and checks its SHA-256.

```text
python -m pytest -q -m "not slow"                  # the checks of Validation §2
python run_case.py evrp E-n22-k4 R1 --time 600     # R0 | R1 | R1-TR | R2-ipm | R2-simplex
python run_case.py transit route100 M1 --until 8   # M0 | M1; --until H cuts the day at H:00
python run_case.py transit route100 M1 --scenario rs1640   # sourced parameters (Data §3)
python run_bench.py                                # tables, figures and the block above
python run_bench.py --grid                         # first recompute the charging-physics grid
python run_baseline.py E-n22-k4 --repo PATH        # evrp-python's GSGA, replayed
```

Each run writes a bundle to `docs/results/`: status, U, L, gap, solver message, time,
code revision, data checksums and parameters, with the replayed routes or schedule.
